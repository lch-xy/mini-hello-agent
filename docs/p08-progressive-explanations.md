# P08 设计详解：原子替换、版本检查与权限边界

配套[架构正文](p08-progressive-guide.md)。四种工具使用目标真实实现，测试仅在临时目录复现副作用与失败。

<a id="p08-a1"></a>
## A1：按意图内聚，按公共可靠性复用

Read 管观察，Write 管整体文本，Edit 管单次唯一替换，MultiEdit 管顺序批次。公共 _atomic_write/_backup_file 统一磁盘落盘规则；Tool/Registry 统一描述、授权、执行和回执。没有额外增加文件服务层或通用事务框架。

工具只完成一次业务操作，下一轮是否继续仍由 Runtime 决定。模型提出请求不证明写入发生；要以真实文件内容和回执检查。

<a id="p08-a2"></a>
## A2：缓存只是证据记录

Read 将请求 path 对应的 mtime/大小放进 Registry.read_metadata_cache；文件工具并不从缓存自动取 mtime 来强制检查。调用方必须显式提供 file_mtime_ms。缓存键也不是规范化后的全局文件身份。

offset/limit 控制返回行范围；当前实现先 readlines 读取文件，不是按范围的底层流式 I/O。返回 file_size_bytes 是整个文件大小，不能把片段长度当作它。

<a id="p08-a3"></a>
## A3：乐观检查降低陈旧写入，仍存在竞争窗口

mtime 检查成本低且能解释冲突，但毫秒取整不等于内容哈希。检查和替换是两个操作；两个写者都可能在同一旧状态检查通过，然后先后替换，最后写入者覆盖前者。

独占临时文件解决临时文件冲突，原子 replace 解决半写入可见性，它们不会把 mtime 检查升级成跨进程排他锁。本阶段忠实复刻该边界，未新增锁或文件根目录限制。

<a id="p08-a4"></a>
## A4：批次原子性来自先准备后提交

MultiEdit 的每一项针对已更新的内存文本验证，失败时直接返回，不触碰原文件或创建备份。全部验证后才调用共用备份和原子写。

这使失败批次不会留下前几项修改，但不提供多文件事务，也不回滚外部并发操作。old_string 的唯一性检查约束精确替换，不进行语义定位或自动猜测。

<a id="p08-a5"></a>
## A5：临时文件必须属于本次操作

同目录 mkstemp 提供独占名称，避免固定 .tmp 被两个写者复用；finally 只删除该名称，不能误删用户的 doc.txt.tmp。原有文件模式通过 copymode 保留，replace 后新内容继承已有执行权限等模式位。

flush/fsync 作用于临时文件，replace 是单次路径替换；这不是对所有文件系统、断电、备份与目录元数据提供完整事务承诺。实际测试关注失败时原文、完整内容可见性和临时文件归属。

<a id="p08-a6"></a>
## A6：备份与展示不能破坏结果语义

备份采用时间戳加独占随机名称，快速多次操作不会覆盖。项目内返回相对展示路径，项目外返回绝对路径；展示格式不能在实际修改成功后抛异常，让调用方误以为未执行。

备份发生在替换之前，因此 replace 失败仍可能留下有效备份。字节变化用 UTF-8 长度计算，不是 Python 字符数量；非 ASCII 场景验证这种区别。

<a id="p08-a7"></a>
## A7：不同控制点不能互相替代

Registry AllowlistPolicy 决定是否允许调用某个工具，不负责解释所有路径。working_dir 解析相对路径，不能阻止绝对路径或所有目录穿越。宿主环境才决定实际文件系统访问许可。

直接调用 Tool.run 会绕过 Registry Policy；框架正常调度路径通过 Registry。mtime 仅检查陈旧观察，不授权访问。学习时需要分别证明调用路径与实际效果，不能只看到 CONFLICT 或 PERMISSION_DENIED 字样就混同机制。

<a id="p08-a8"></a>
## A8：从可见副作用反推责任

纵向场景的模型只负责确定性地安排 Read/Edit；工具实际读写，Registry 实际调度，Runtime 实际回写 ID。最后文本相同不足以证明操作发生，因此同时核对磁盘、备份和调用关系。

本地历史 `9ff239a` 到 `1650f26` 展示当前文件工具演进；固定目标已经采用独占临时文件、顺序批改和外部备份展示。讲解验收：原子性与并发协调有什么区别？缓存是否自动加锁？批次第二项在哪个版本上校验？replace 失败时备份是否可能已经产生？谁决定能访问项目外路径？
