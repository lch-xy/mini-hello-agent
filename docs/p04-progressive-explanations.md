# P04 设计详解：流能力、消费方式与执行生命周期

配套[架构正文](p04-progressive-guide.md)。每节解释为什么选择该方案，以及它实际保证到哪里。

<a id="p04-a1"></a>
## A1：共同契约先于入口数量

四个方法签名只是表面接口。真正要统一的是模型调用次数、实际工具副作用、原生消息关系、最终状态和收尾。如果入口分别组织循环，普通调用与流式调用很容易在错误处理中产生不同历史。

把 _events 作为共同执行源后，run/arun 取最终答案，stream_run 筛公开文本，arun_stream 交出类型化事件。策略执行是同一份，展示层可独立选择消费形式。

<a id="p04-a2"></a>
## A2：复用执行语义需要承担桥接成本

异步核心允许在等待模型、工具和事件时把控制交还宿主。同步代码使用专用事件循环逐步消费，并在退出时关闭异步生成器和线程执行器。已经运行的事件循环不能再嵌套 run_until_complete，因此同步入口明确拒绝该用法。

同一个 Agent 还有可变历史和 last_run；模型客户端线程安全不代表会话状态可并发修改。_run_active 保护的是会话推进，不是跨进程锁或整个系统的调度器。独立任务使用独立 Agent，仍可按宿主策略共享模型和工具。

<a id="p04-a3"></a>
## A3：为什么工具流需要终态响应

展示文本允许增量；执行工具需要完整名字、参数和身份。适配器以 index 累积多条工具请求的碎片，直到流结束才生成 ToolCall 列表，Runtime 再统一校验 ID、停止信息和参数。

usage 可能只存在最后一个 choices=[] 的包里，若先因没有 choices 而 continue，就会丢掉统计。当前先读取 usage，再处理内容/工具。私有 reasoning_content 被保留到完整响应和原生历史，公开字符串只包含可见内容；think 只是文本流别名，不保证自动开启模型推理模式。

<a id="p04-a4"></a>
## A4：Adapter 保持契约，能力差异仍然存在

这里使用的模式仍是 P01 的 Adapter 加公共门面：协议碎片、客户端和转换细节归各适配器，Runtime 面向统一响应。没有为每个提供商增加新的 Agent 或循环。

BaseLLMAdapter 的文本异步回退用后台线程消费同步流，队列容量为 8，队列满时生产者等待。工具流回退则等待一次非流式调用，最多给出一段完整内容后给完整响应；这兼容消费协议，但不会降低首字延迟。

OpenAI 原生工具流使用每次请求单独创建的异步客户端并关闭它；文本异步入口复用适配器的 _async_client，由模型 close/aclose 释放。不能把两条路径的客户端所有权混为一谈。

<a id="p04-a5"></a>
## A5：关闭传播依靠结构化收尾

yield 暂停了生成器，退出 async for 本身不等于所有嵌套源都立即关闭。目标使用 aclosing 和 finally 将运行拥有的生成器逐层关闭；宿主仍应显式关闭不再消费的 arun_stream，并最终关闭自己拥有的模型。

同步 SDK 读取或同步工具可能在线程中阻塞。取消 await 只能停止等待；文本回退的停止标记会阻止读取返回后的下一次拉取，不能终止正在执行的阻塞操作。资源回收与外部副作用确认是两个问题。

<a id="p04-a6"></a>
## A6：三个时限对应三个责任

模型读取时限约束当前 anext；工具时限约束实际调度等待；钩子时限约束观察者。前两者失败影响执行状态，后者不能用自己的异常覆盖业务完成。deadline 还要识别自己的取消请求，避免把宿主的独立取消错误改成超时。

模型读取完成后把片段交给消费者，此时不应继续计算读取时间。用户停顿、浏览器慢渲染或网络发送慢属于消费时间。阶段测试故意让消费者停得比模型时限还长，并检查关闭依然成功。

<a id="p04-a7"></a>
## A7：unknown 是执行证据的边界

确认回执证明框架取得了结果；缺回执只证明框架未确认。同步线程可能在取消之后完成写入，因此补 unknown 比补“已失败”更准确，恢复方也不能仅凭中断就重复写入。

历史在 AGENT_FINISH 发出之前提交。消费者收到完成事件就关闭时，不能反过来把已经完成的任务改成取消。若中途关闭，则保留已确认回执，补齐未确认 ID 并清理 _run_active。存盘与重启组合在 P09 完整验收，本阶段不把回执检查冒充全套持久化验证。

<a id="p04-a8"></a>
## A8：事件契约与网络帧的职责不同

StreamEvent 是运行展示契约，SSE 是传输编码。to_sse 序列化 event/data 与空行边界；字节分块和重组属于宿主传输/前端。测试中的增量解码器只是消费者验证，没有向框架新增前端解析器。

StreamBuffer 的丢旧保新是有限事件缓存，并不对生产者施加背压。容量 8 的线程队列才在生产与消费之间阻塞等待。学习设计模式时要依据行为判断，不能只根据类注释里的“背压”一词认定能力。

本阶段保留 P01 已有中文注释，仅加入目标原始流方法；P03 的 Runtime/生命周期实现无需重写。`52b2597` 的适配器变更展示缺失 choices 等协议修复，`1650f26` 提供当前统一执行和收尾实现。历史对照以本地 diff 为证据，不推测事故与作者动机。
