# P16 设计详解：先建立可回读的关系，再扩大图能力

对应[架构递进](p16-progressive-guide.md)。本阶段的思考顺序是：查询目的→证据契约→有效性→遍历控制→工具组合，不从数据库选型或图算法名称开始。

<a id="p16-a1"></a>
## A1：从查询问题选择最小方案

| 方案 | 收益 | 当前取舍 |
| --- | --- | --- |
| 反复词项检索 | 复用 P13，无关系表 | 没有显式方向和有界拓扑，不能表达两跳契约 |
| 同 SQLite 保存带证据关系 | 与当前版本关联直接、部署简单 | 当前采用；依赖宿主统一精确实体并导入关系 |
| 独立图数据库 | 更丰富的图查询和运维能力 | 当前需求不需要另一套服务、身份与同步边界 |

先实现显式输入、确定遍历与可回读证据，便于把后续模型抽取造成的错误，与持久化/查询错误分开定位。GraphRAG 的社区报告和全局综合是 P17 的新增需求，不能因已有一个图就声称完成。

<a id="p16-a2"></a>
## A2：关系表保存关联，原文仍只有一个权威

RelationStore 依赖现有 RAGStore，在同库创建关系表与 subject/object 索引。add 读取 chunk，检查所有字段非空、quote 为片段连续子串，按输入字段计算稳定关系 ID，INSERT OR IGNORE 实现同输入幂等。

quote 定位只验证原文里出现过这段话；subject/predicate/object 是宿主提供的声明，不由子串检查证明正确。原文“有人声称 A 导致 B”也不能因此升级成因果事实。这里无需新增万能 Repository 抽象：同库与版本 JOIN 是实现的明确耦合，抽象必须服务后续变化才值得加入。

<a id="p16-a3"></a>
## A3：权威版本决定边是否参与当前查询

查询关联 rag_relations→rag_chunks→rag_documents，要求 chunk.version 等于文档当前 version 且 active=1。旧边无需先物理删除就能退出当前结果，资料撤下同样生效；read_chunk 仍可回读历史证据。

add 的 quote 检查本身不限制历史 chunk，当前查询的 JOIN 才承担可见性。不假设有后台自动重抽取，也不把本地读取称为跨进程图快照事务；并发全图构建的发布一致性要到 P17/P18 讨论。

<a id="p16-a4"></a>
## A4：BFS 的状态各有单一目的

以 out、hops=3、环 A→B→C→A 为例：

| 扩展节点 | 队列动作 | 新返回边及 depth |
| --- | --- | --- |
| A,0 | B 首次出现，入队 B,1 | A→B，1 |
| B,1 | C 首次出现，入队 C,2 | B→C，2 |
| C,2 | A 已 visited，不再入队 | C→A，3 |

queue 决定逐层扩展，visited 控制节点只扩展一次，edges 控制同一关系不重复输出，results 控制返回上限。仅 visited 不足以去重 both 方向重复遇见的边，仅 edges 也不能阻止重复排队扩展。depth 表达发现该边的层次，不是三元组本身的权重或一条独立因果链。

<a id="p16-a5"></a>
## A5：先明确可预测的上限，再谈排名

out 从 subject 找 object，in 反向，both 沿两端扩展。队列与每节点按 relation_id 排序提供确定的发现顺序；limit 提前终止，未返回不代表图中不存在。高出度中心一跳就可能超过 limit，深度上限不能替代结果上限。

精确实体字符串由宿主规范化；当前不做别名消歧、语义种子、社区汇总或向量召回。bool 虽是 Python int 子类，但目标用 type 检查拒绝 bool 跳数，避免参数意义含混。Schema 可帮助模型生成参数，Store 仍独立验证边界。

<a id="p16-a6"></a>
## A6：以协议适配保持工具和算法低耦合

RelationTool 是薄适配层：调用 neighbors、序列化结果、映射无效参数；Store 拥有全部遍历状态，Agent 只认识 ToolRegistry/ToolResponse。模型获得只读查询入口，写入仍由宿主显式操作，避免将未经审核的抽取偷偷接进事实库。

这体现读写职责分离，但不需要引入完整 CQRS 基础设施；结果转换是适配，不必把每个辅助方法都称为设计模式。高内聚是“关系不变量集中在 Store”，低耦合是“新增关系能力不更改 Runtime 循环”。

<a id="p16-a7"></a>
## A7：持久化与消费共用相同证据身份

RelationResult 包含三元组、quote、RetrievalResult 和 depth；to_context_packet 保留 relation/source/version/chunk_id，to_dict 递归保留完整证据。宿主可通过 ContextPacket 或 ToolResponse 消费它，不能捏造一个目标没有的自动 Provider。

重开数据库证明关系不是内存缓存；读取原 chunk 证明来源链可追溯。这些保证不等于关系正确、资料现实有效，也不保证两个边串起来必然存在可执行路线。引用核对和业务审核各自承担不同职责。

<a id="p16-a8"></a>
## A8：验收针对架构的变化边界

完整原 test_retrieval_composition 覆盖链/环/深度、方向、返回上限、重开持久化、坏 quote 拒绝、原文更新使旧边退出、精确实体、不合法参数和 Registry 回执；也恢复 P14 管线原始组合断言。已存在这些有意义检查，不再为简单导出重复编写镜像测试。

历史中当前 relations/relation_tool 由 1650f26 引入。学习次序是在这个特性提交中拆出最小关系查询层，而不是把 Git 提交标题当作架构设计说明。下一阶段才加入模型抽取、规范化实体、真实 Leiden 社区与版本化图代次。
