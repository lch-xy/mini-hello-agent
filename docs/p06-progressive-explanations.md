# P06 设计详解：上下文控制的职责与损失

配套[架构正文](p06-progressive-guide.md)。组件已经在 P03 依赖链落地，本阶段以行为验证解释其架构分工。

<a id="p06-a1"></a>
## A1：四种信息寿命

HistoryManager 保存跨轮交互，本次 messages 记录运行中请求与回执，Builder 输出仅服务当前模型请求，长工具完整结果文件提供后续回读。它们寿命不同，不能让一次资料选择直接编辑全部历史。

Builder 深复制基础消息；Provider 资料是临时加入的参考消息。Runtime 继续保存原始工具交互，运行成功后按整轮提交。这样更新资料选择策略不会改变实际执行证据。

<a id="p06-a2"></a>
## A2：保留完整轮不等于绝对容量保证

HistoryManager 用 user 消息索引定位轮次，压缩旧前缀并保留最近 N 轮。对于常规工具往返，它保住 assistant/tool 关系；但它不理解真实外部用户任务边界，策略内部的 user 角色提示也会计为边界。

最少保留轮次优先于压缩尺寸，所以一轮巨大输入仍可能超预算。Builder 的基础消息超限检查是独立保障，不能从“启用了历史压缩”推导永远能调用模型。

get_history 只复制列表，修改返回列表不会删除内部历史，修改其中 Message 则仍可能影响同一对象。框架没有把整个历史设计成持久化不可变数据结构。

<a id="p06-a3"></a>
## A3：估算器的边界必须可见

TokenCounter 按模型编码计算文本，并将原生工具请求与回执 ID 纳入缓存键；失败时按字符数除四降级。它不等于完整 SDK 序列化请求的精确 Token 数，也不自动等于计费 usage。

Builder 使用 cl100k_base 或字符估算，并计入基础消息 JSON、Schema、参考消息包装和元数据。两者数值可能不同；diagnostics.is_estimate 明确说明性质。不要为了“统一数字”合并职责或声称输入成本准确到每个 Token。

<a id="p06-a4"></a>
## A4：摘要是有损转换

简单摘要只保留统计，旧事实会丢失；智能摘要有保留事实的目标，但仍依赖模型质量，且格式化输入会限制每条消息长度。最近原文轮次保留正是对损失的部分补偿。

智能摘要从同一实际保留边界取旧前缀；主模型可复用，独立模型须注入完整实例。普通异常回退统计摘要意味着降级后信息更少，应明确可见；BudgetExceeded 不回退，保留运行预算的准入语义。完整资源消耗统计仍待 P18 接通。

<a id="p06-a5"></a>
## A5：预览与完整结果之间建立可回读关系

Truncator 是工具输出的统一策略，业务工具不需要理解上下文窗口。先选行再限字节，边界字符以有效 UTF-8 方式保留；完整 JSON 含工具名、原文和元数据。

Agent 再把截断结果包装为 partial 观察及路径。文件回读是后续工具能力，保存原文不保证模型马上知道全部事实，也不保证预览中一定含有最相关证据。方向选择表达保留头尾的策略，不等价于语义摘要。

<a id="p06-a6"></a>
## A6：选择算法与权限角色各自独立

相关度来自查询词项重叠；中文以单字/相邻双字分词。MMR 用词项 Jaccard 相似度抑制重复，仍是词法启发式，不是语义向量检索。ContextPacket 自带 relevance_score/token_count 不直接决定这里的选择或最终总预算。

required 与 instructions 类型影响保留优先级，不赋予 system 角色。选中资料保留来源元数据，以 user 参考插入当前任务前；预算始终保护已有基础消息，放不下可选包就整包排除，required 放不下则失败。

<a id="p06-a7"></a>
## A7：用 Protocol 限制知识依赖

Provider 只需 get_context，Assembler 只需 build_messages。Agent 不需要导入具体数据库或知道 RAG/Memory 内部表结构；后续可以换成不同来源和组装实现，而不复制 Runtime。

每次请求重新收集能观察同任务内的撤回更新，但不会抹掉历史中实际发生的工具结果，也不等于强制模型遗忘。P06 的真实函数修改本地 Provider 场景验证调用时机，P13/P15 再验证真实存储版本和范围。

<a id="p06-a8"></a>
## A8：边界冲突比单组件成功更能说明设计

历史保留、观察预览和输入选择同时存在时，不能假设一个组件成功便代表整项输入有效。当前测试分别保留最近轮、限制 UTF-8 字节、计入 Schema、拒绝基础/required 超限，并在真实工具后重新组装。

讲解验收：超大单轮为何可能仍超限？计数器与服务 usage 为什么不同？统计摘要丢什么？required 包超限谁处理？资料中的系统指令会成 system 消息吗？Provider 为什么每次请求刷新？回答应沿数据流定位责任，而非逐行复述代码。
