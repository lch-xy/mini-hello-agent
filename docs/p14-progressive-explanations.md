# P14 设计详解：发布代次、召回融合与排列约束

配套[架构正文](p14-progressive-guide.md)。向量、融合和重排改变检索方式，不能改变权威证据。

<a id="p14-a1"></a>
## A1：索引是派生数据

SQLite 保存原文、版本和当前集合；Qdrant 点只携 chunk_id 等索引载荷。命中再回读 Store，避免载荷成为另一份可能过期的文本权威。

namespace 区分资料库，revision 表示当前集合，model_id 表示编码空间/预处理，generation 表示一次构建。它们解决不同变化，不能只校验维度或文档版本。

<a id="p14-a2"></a>
## A2：编码协议与模型配置分离

文档/查询可能需要不同前缀与编码入口，因此 Protocol 明确两种方法。OpenAIProvider 以 input index 恢复顺序；validate_vectors 检查数量/维度/有限/非零，但不宣称向量已单位化或语义正确。

FastEmbed 首次 _load 才构造模型，可能下载权重。本阶段安装 SDK、核对 passage_embed/query_embed 入口，用注入假向量验证协议；不把它称为真实模型质量评测。云端配置则发送 Qdrant Document 文本，由服务编码。

<a id="p14-a3"></a>
## A3：集合兼容性和客户端所有权各自校验

单个余弦向量的集合配置必须匹配维度；已有 namespace manifest 必须匹配 model_id。相同维度不保证相同模型空间，换预处理需新身份/集合。

path/url 创建的 client 由索引拥有，注入 client 由宿主关闭。CloudInference 只允许 HTTPS/key 的 URL 配置，并预建关键词过滤字段索引；HTTP 协议夹具验证这些请求结构，不证明真实云账号和服务可用。

<a id="p14-a4"></a>
## A4：发布与回收分开，失败不会暴露半个新集合

新代次点上传完成且 revision 仍匹配后，写固定 manifest 点切换可见性。查询只读清单指定代次，旧代回收失败也不会混入新结果。上传中断可能留下不可见点，后续维护处理。

这是代次发布方案，不是 SQLite/Qdrant 两系统的事务提交。实例 RLock 不协调不同进程，宿主需要单写入任务；发布后资料又变化时查询会判过期，不能从一次 revision 检查推出全局锁。

<a id="p14-a5"></a>
## A5：过滤之后仍回读原文

清单先确认当前 revision，向量查询再过滤 namespace/kind/generation/model_id，命中逐条查 SQLite chunk 与当前文档状态，末尾检查 revision。缺原文、旧版本和中途变化都明确拒绝。

这使恢复和引用沿用 P13 身份，不为向量结果创造新证据。IndexStaleError 要求显式 sync，而非把错误隐藏成“可能相关”的旧内容。

<a id="p14-a6"></a>
## A6：RRF 融合的是排名

每路最多 candidate_limit 条，排名从 1 开始累加倒数贡献。原始得分量纲被隔离，返回记录用融合分数；同 ID 的内容/来源等必须一致。

Hybrid 检查各后端公开的 Store revision，避免拼接不同时间的结果。它不自动为所有自定义后端创造版本协议；宿主应提供一致的证据来源和变化信号。

<a id="p14-a7"></a>
## A7：完整排列把模型自由度限制在顺序

LLMReranker 只让模型返回候选索引，Pipeline 再检查所有原记录完全相等；模型重排分数不覆盖召回证据。输入超限提前失败，输出截断即使碰巧是合法 JSON 也拒绝。

重排只能改善已召回集合，不能挽回全部漏召回。调用注入 LLM 也会增加一次模型请求；当前脚本响应只验证约束，不衡量真实相关性或通用效果。

<a id="p14-a8"></a>
## A8：指标必须有显式真值与实验边界

ranking_metrics 检查唯一 IDs 和有限 0–10 标注，计算二值 Recall/MRR 与分级 nDCG；没有正相关真值则未定义。evaluate_retrieval 记录逐查询结果和延迟，平均值只纳入已定义项。

自带 Qdrant 示例使用虚构旅行资料并要求显式模型/维度，可在之后独立运行；本阶段不下载权重或调用真实嵌入服务。讲解验收：失败代次为什么不可见？清理失败后新索引为何仍可用？RRF 为何不加原始分数？重排为何不能改 score？None 与零分有什么区别？
